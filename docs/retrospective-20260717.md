## 2. 细节核验发现的偏差（需修正）

- **账本数字错误（重要）**：看板第 7/8 节写"约 333 图，120 换 / 213 留"——与 git 真相 **183 换 / 287 留** 不符。根因：决策日志（`p*_quality_decision_table.log`）跨多轮跑、部分陈旧，且只覆盖 MinerU 有输出的 333 张；另有 **137 张图 MinerU 从未处理**（直接留原图），未被计入。→ 已修正看板，后续以 `git diff` 为唯一计数源。
- **p1 闸门反转过宽**：p1 早期章（ch01–06）原图确为 1700px 整页渲染（已抽样证实 1700×875 / 959 / 754），反转闸门合理；但 **p1-ch10 等后期章原图是正常裁切（1024×778）**，也被一律反转换图。净效果仍优于原整页 blob，但部分 p1 换上的线稿是"小裁切"（如 298×401），fidelity 有提升空间。
- **p3 决策日志用了不同闸门**（按 W&H≥原图，而非提交的 area≥95%）。p3 换上的 42 张与看板一致，但 provenance 不一致，需在最终 QA 复核 p3 换图是否混入被降采样的线稿（风险低：p3 原图是正常裁切，近似闸门多换照片类）。
- **"宽高比畸变"是误报**：Agent 把 p1 换图 vs 1700 整页原图比出 42–73% "畸变"——这其实是**整页渲染被替换成真实裁切小图**，属正确行为，非缺陷。

## 3. 发散排查：被忽略的隐患

- **H1 漏换图（高优先核查）**：日志出现 "extra MinerU image, no caption"（p3 ch07-15、p1 md 707–719 区间）——MinerU 检出了图但脚本未换 / 留孤儿。这些**可能本该换却漏了**。
- **H2 假阴性（可升级项）**：日志里约 87–94.9% 面积的线稿被 0.95 闸门卡掉（其实 MinerU≈原图、换了也安全）；多面板图 MinerU 把每小面板都满分辨率抽出——**应重组而非留降采样原图**。
- **H3 留图质量无感知核验**：183 张换图靠"面积≥95%"逻辑判定更优，但**尚未有人眼验收**（看板仍"待用户验收"）。逻辑说更优 ≠ 视觉更优，这是当前最大剩余风险。
- **H4 多面板 64 张 + 1700 整页 64 张（p1）留原图**，本质是因 MinerU 把整页/多面板当位图降采样，留了更差的原始——这两类恰恰是"直接高 DPI 从 PDF 抽"能根治的。

## 4. 更好的解决方案（网络调研支撑）

**核心洞察**：MinerU 是版面+内容解析器，不是图保真工具——它把所有图（含矢量线稿/曲线图）都光栅化并降采样，故对线稿反而不如原图（与本项目实测一致：照片类 MinerU 更清、线稿类被压窄）。

| 方案 | 做法 | 依据 | 收益 |
|---|---|---|---|
| **S1 最优提取管线（首推）** | 用 MinerU 的 middle.json **只做定位**（page+bbox，它 98% 准），再用 **PyMuPDF / pdf2svg 从源 PDF 按 bbox 抽**：线稿/曲线图→**SVG**（无限缩放、体积小、矢量锐利）；照片→**高 DPI(300+) PNG/JPG** | PyMuPDF `get_svg_image()` + `get_drawings()` 裁剪到矢量边界；pdf2svg/Inkscape 同理 | 同时升级已换的 183 张和留的 287 张；线稿彻底告别降采样 |
| **S2 SVG 化线稿** | 所有示意图/曲线图用 SVG（Web 原生、缩放不糊） | 学术图规范：矢量图用 PDF/SVG，绝不用 JPG 存线稿（会产生锐边噪点） | 网页端任意放大清晰、文件更小 |
| **S3 高 DPI 光栅抽照片/多面板** | `pdftoppm -r 300` 或 PyMuPDF 矩阵缩放，从源 PDF 直接抽整图/每面板 | 期刊规范：线稿 1000–1200dpi、照片 300dpi、混合 600–900dpi | 多面板 64 张、1700 整页 64 张一次性解决 |
| **S4 Real-ESRGAN 仅作兜底** | 仅对**确实无矢量/高 DPI 源的低位照片**做 2–4× 超分 | 腾讯 Real-ESRGAN：善救老照片/扫描件，但**会"脑补"细节、绝不可用于线稿/文字（会幻觉笔画）** | 兜底 28 张"MinerU 无输出"的照片类 |
| **S5 统一闸门+账本** | 用 git diff 计数、单一种子闸门重跑 | 本次账本偏差教训 | 计数可信、可复现 |

**结论**：当前混合方案是"局部最优"，S1 是"全局更优"且**自动化可行**（MinerU 已给 bbox，写个 PyMuPDF 抽取器即可），能把 183 换 + 287 留全部升一档。
